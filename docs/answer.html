Справочник «ИНН → сайт организации». Репозиторий с кодом (Задание 2): {{REPO_URL}}

Задание 1. Как собрать и поддерживать справочник

1. Постановка и допущения

  • Объекты: действующие юрлица и ИП из ЕГРЮЛ/ЕГРИП (по порядку величины 3 млн ЮЛ и 4 млн ИП). Филиалы — по ИНН головной организации.
  • Сайт организации — домен, который она контролирует и на котором выступает владельцем, продавцом или исполнителем. Не считаются: карточки на агрегаторах и картах, страницы в соцсетях, магазины на маркетплейсах, поддомены конструкторов (*.tilda.ws). Сайт группы компаний засчитывается, если на нём указаны реквизиты именно этой организации.
  • Формат ответа: список доменов, основной первым — как поле data.sites[] в ответе «Организация по ИНН».
  • Главная метрика — точность (precision). Справочник используют для проверки контрагентов, обогащения CRM, антифрода: неверный сайт в ответе вреднее пустого поля. Полнота (recall) — вторая по важности.

2. Способы сбора данных

СпособКак работаетЗаПротив
1. Обход доменов (домен → ИНН) Все домены зон .ru/.рф/.su (списки зон, порядка 6 млн) + новые домены из CT-логов. Качаем главную и «Контакты / Реквизиты / Политику ПДн», извлекаем ИНН/ОГРН. ИНН публикует сама компания — высокая точность. Продавцы обязаны указывать наименование и ОГРН (ЗоЗПП), операторы ПДн — реквизиты в политике (152-ФЗ). Стоимость зависит от числа доменов, а не организаций. Своя инфраструктура обхода. ИНН встречается и на чужих сайтах (политики ПДн с перечнем третьих лиц, «наши клиенты»): нужна классификация контекста. Не находит сайты без реквизитов.
2. Открытые реестры с полем «сайт» ЕИС закупки, раскрытие информации эмитентов, реестры ЦБ (банки, страховщики, МФО), реестр аккредитованных ИТ-компаний, реестры лицензий. Официальные данные, дёшево, высокая точность. Малая и смещённая доля: в основном крупные и регулируемые организации.
3. Домен корпоративной почты E-mail из ЕГРЮЛ/контактов DaData (заполнен у ~50% действующих компаний): info@firma.ru → firma.ru. Данные уже есть, почти бесплатно. Бесплатные почтовые сервисы неинформативны. Почтовый домен — не всегда сайт (сайта нет, домен бухгалтера или хостера). Сильный кандидат, но не доказательство.
4. Поиск + LLM (Задание 2) Поиск по ИНН, ОГРН и названию, проверка найденных сайтов, решение LLM по спорным случаям. Закрывает «хвост»: сайты без ИНН, бренды, не совпадающие с юрназванием. Стоимость и время на каждый ИНН, зависимость от индекса поисковика. На 7 млн ИНН дорого.
5. Агрегаторы и карты (Rusprofile, 2ГИС, Яндекс Бизнес) Покупка данных, партнёрство или парсинг. Большое покрытие. Вторичные данные с ошибками; права изготовителя базы данных (ст. 1334 ГК РФ) и условия использования; часть агрегаторов скрывает поле «сайт».
6. WHOIS/RDAP Для доменов .ru/.рф, зарегистрированных на организацию, указывается её наименование. Независимый сигнал владения доменом. Только название, без ИНН; доступ ограничен.

Выбор. Ни один способ не даёт одновременно покрытие и точность. Поэтому архитектура — «кандидаты из нескольких источников → единая проверка → решение по доказательствам»:

  1. Генерация кандидатов. Основной массовый источник — обход доменов (1). Дополняют: домены почты (3), реестры (2), поле «сайт» агрегаторов (5) — только как кандидат, не как истина.
  2. Единая проверка для всех источников (реализована в Задании 2): загрузка сайта, поиск ИНН/ОГРН/названия, определение контекста — это реквизиты владельца сайта или упоминание третьего лица. LLM — только для неоднозначных случаев.
  3. Решение по уровню доказательства, а не по «вероятности»: A — ИНН/ОГРН на сайте в роли владельца; B — название + адрес/телефон на сайте + независимый источник (почта, реестр, агрегатор); C — только совпадение названия → не публикуется.
  4. Поиск + LLM (4) — только для дозаполнения: ИНН, которые часто запрашивают в API, но сайт для них не найден способами 1–3. Дорогой метод тратится там, где результат видят клиенты.

Почему основа — обход доменов: стоимость пропорциональна числу доменов, а не организаций; доказательство берётся из данных самой компании; процесс детерминирован и воспроизводим. {{T1_EVIDENCE}}

3. Анализ и оценка качества

  • Метрики:
    • precision — доля верных доменов среди опубликованных;
    • recall — доля найденных среди организаций, у которых сайт есть;
    • coverage — доля ИНН с непустым ответом.
    Все метрики считаются в разрезах: ЮЛ/ИП, размер (выручка, численность), регион, ОКВЭД, возраст компании, источник, уровень доказательства. Отдельно — с весами по частоте запросов ИНН в API, чтобы мерить качество там, где его видят клиенты.
  • Эталон:
    • стратифицированная случайная выборка из ЕГРЮЛ/ЕГРИП, 1–2 тыс. ИНН, с перевесом редких страт и весами для пересчёта на генеральную совокупность;
    • разметка двумя асессорами по инструкции (определение сайта, спорные случаи), согласованность по каппе Коэна, арбитраж;
    • метка «не удалось установить» (сайт скрыт, противоречивые данные) исключается из метрик и учитывается отдельно.
  • Дешёвая оценка precision: отдельная выборка из опубликованных ответов. Проверить, что сайт верный, проще, чем найти его с нуля. На 1000 ответах 95%-й доверительный интервал (Уилсон) — около ±1,5 п.п. при precision 95%.
  • Калибровка: для каждого уровня доказательства (A/B) измеряем precision. Публикуем только уровни, которые дотягивают до целевого порога (например, 95%).
  • Ловушка — смещение эталона. Если положительные примеры набирать через страницы реквизитов, у всех них ИНН на сайте есть, и recall для сайтов без реквизитов окажется завышен. В Задании 2 так набрана часть выборки; это учтено при интерпретации результатов.
  • В эксплуатации:
    • ежемесячный аудит случайной выборки опубликованных записей;
    • мониторинг доли «мёртвых» доменов, изменившихся ответов и жалоб клиентов;
    • канал «сообщить об ошибке» в API или личном кабинете.

4. Поддержание актуальности

  • Модель данных:
    • ИНН, домен, источник, уровень доказательства;
    • URL страницы и фрагмент с доказательством;
    • first_seen, last_verified, статус (активен / не отвечает / снят), история изменений.
  • Проверка по событиям:
    • ЕГРЮЛ: ликвидация → снять связь; реорганизация → проверить правопреемника; смена названия или адреса → перепроверить;
    • домен: смена регистранта, снятие с делегирования, истечение срока регистрации → перепроверить. Истёкший домен могут перекупить, и под старой связью окажется чужой сайт;
    • сайт: ИНН исчез со страниц, появился редирект на другой домен → перепроверить;
    • новые домены: ежедневные изменения зон и CT-логи → обход.
  • Плановые проверки:
    • доступность (DNS/HTTP) — еженедельно;
    • полная перепроверка реквизитов — раз в 1–3 месяца, для популярных ИНН — чаще;
    • отрицательные ответы («сайта нет») — повторная проверка через 1–3 месяца (в прототипе — через 30 дней).
  • Снятие связи: после нескольких неуспешных проверок подряд — статус «не отвечает»; через N недель — удаление из ответа API (в истории запись остаётся).

5. Открытые вопросы, проблемы и ограничения

  • Что считать основным сайтом:
    • холдинги (один сайт — много ИНН);
    • сети и бренды (один ИНН — много сайтов);
    • дилеры и франчайзи (сайт дилера под брендом производителя).
    Нужны продуктовые правила и тест-кейсы.
  • Площадки: для малого бизнеса единственным присутствием в сети часто бывает магазин на маркетплейсе, страница VK или Telegram. Решение: отдельные поля (social, marketplaces), а не смешивание с sites.
  • ИП:
    • связка «физлицо — сайт» — это персональные данные: нужно правовое основание обработки и процесс удаления по запросу;
    • покрытие ниже: сайт у ИП бывает реже, а ФИО — неуникальный ключ для поиска.
  • Мошеннические клоны копируют реквизиты настоящих компаний, поэтому «ИНН на сайте» ещё не означает «сайт компании». Сигналы подделки: молодой домен, другое название в WHOIS, контакты не совпадают с ЕГРЮЛ, несколько доменов претендуют на один ИНН. При таких сигналах связь уходит на ручную проверку.
  • Юридические риски сбора: условия использования агрегаторов, права изготовителя базы данных, robots.txt и нагрузка на сайты при обходе.
  • Технические:
    • защита от ботов и сайты, которые рендерятся только JavaScript-ом;
    • сайты в иностранных зонах (.com, .io) нельзя перечислить заранее — их находим только через поиск и CT-логи.
  • LLM:
    • стоимость и недетерминированность;
    • контентные фильтры: в Задании 2 GigaChat отказывался отвечать на пакетах кандидатов, где встречались страницы о санкциях;
    • риск галлюцинаций. Поэтому решение принимает правило, а LLM даёт только категорию и цитату, которую проверяет код.
  • Экономика: ключевая метрика — стоимость одной подтверждённой связи по каждому источнику. Дорогие методы применяем только к востребованным ИНН.
