Задание 2. Пайплайн «ИНН → сайт» (Web Search + LLM)

Код: {{REPO_URL}}. Python 3.12, запуск: uv run python -m site_finder 7721581040 → {"domain": "dadata.ru", "sites": ["dadata.ru"]}. domain — основной сайт (формат из задания) или null; sites — все подтверждённые домены (совместимо с data.sites[]).

Общая логика

Это workflow с агентным шагом, а не автономный агент. Шаги задаёт код. LLM принимает решения в двух местах: оценивает каждый найденный сайт и, если подтверждённого сайта нет, сама формулирует новые поисковые запросы. Принцип: доказательства собирает код, LLM интерпретирует контекст, решение принимает прозрачное правило.

ИНН → валидация → справочник data/directory.csv (уже проверяли? → ответ)
  → карточка ЕГРЮЛ/ЕГРИП: название, ОГРН, адрес, e-mail
  → поиск Exa + DuckDuckGo: "ИНН" · "ОГРН" · название + город (ИП: ФИО + город)
  → кандидаты: домены из выдачи + домены со страниц с ИНН компании (агрегаторы:
               «Сайт: …», «E-mail: info@…») + домен почты из ЕГРЮЛ
  → проверка кодом: главная, Реквизиты/Контакты/О компании/Политика ПДн,
               страницы домена из выдачи → флаги ИНН/ОГРН/название + фрагменты
  → GigaChat-2-Max: вердикт по каждому кандидату + цитата-доказательство
  → правило; сайта нет → GigaChat предлагает до 3 новых запросов → 2-я итерация
  → {"domain", "sites"} + запись в справочник + трассировка logs/<ИНН>.json

Инструменты

КомпонентВыбор и причина

Ключевые технические решения

  1. Проверка реквизитов кодом до LLM. ИНН/ОГРН ищутся регулярным выражением, с учётом пробелов («7721 581 040»). Это главный рычаг точности: факт, а не мнение модели.
  2. LLM даёт категорию, а не вероятность. Вероятности, которые модель выдаёт словами, не откалиброваны. Вместо них — вердикт из фиксированного набора: own_site / group_site / third_party_mention / unrelated. Главная задача LLM — отличить собственный сайт от упоминания третьей стороной: на ИНН DaData поиск выдаёт десятки сайтов автодилеров, где «ООО "Дейта Кью"» — обработчик данных в политике ПДн.
  3. Вместо «reason» — цитата, которую проверяет код. Свободное обоснование в ответе не нужно. Модель обязана привести фрагмент страницы, на котором основан вердикт. Код проверяет, что все числа из цитаты есть на странице и что не меньше 85% её слов встречаются в тексте страницы (без учёта пробелов: Exa отдаёт текст со склеенными словами). Дословное совпадение не требуется: модель переписывает таблицы реквизитов в списки, и при строгой проверке терялся верный sberbank.ru.
  4. Прозрачное правило решения:
    • принять, если ИНН или ОГРН есть на сайте и LLM подтвердила own_site или group_site;
    • принять, если на сайте есть название, есть независимый источник (домен упомянут на странице с ИНН компании или совпадает с почтой из ЕГРЮЛ) и LLM подтвердила own_site;
    • иначе — null.
    Правило настраивается на размеченной выборке, каждое решение видно в трассировке.
  5. Без LangGraph. Поток почти линейный: один цикл максимум из двух итераций и одна развилка. Всё, ради чего берут LangGraph, здесь не нужно: сохранение состояния, возобновление после сбоя, участие человека, параллельные ветки, несколько агентов. Обычный Python короче, логика видна целиком, меньше зависимостей.
  6. Workflow вместо автономного агента, где LLM сама выбирает инструменты: предсказуемая стоимость (не больше 2 итераций, до 8 кандидатов на итерацию), воспроизводимость, качество легко измерить. Платим за это гибкостью в нестандартных случаях.
  7. Агрегаторы распознаются по общим признакам, а не по чёрному списку. Агрегаторов сотни, список не бывает полным. Признаки «страницы-каталога»: ИНН или ОГРН компании в URL или заголовке, длинный числовой ID в пути (/id/3197573), четыре и больше разных ИНН на странице. Такие страницы не считаются доказательством для своего домена. Без этого rusprofile.ru выглядел бы «сайтом с ИНН компании» — так было в первой версии: 6 ложных срабатываний на 56 ИНН. Площадки (соцсети, маркетплейсы, бесплатная почта) получают низкий приоритет, но не исключаются: у Ozon, HeadHunter, Яндекса это и есть собственный сайт.
  8. Устойчивость к отказам GigaChat. Фильтр модели срабатывал (finish_reason=blacklist) на пакете кандидатов, где была страница о санкциях, и ответ пропадал для всех кандидатов сразу. Теперь при отказе каждый кандидат оценивается отдельным запросом, отказ затрагивает только «чувствительную» страницу.
  9. Сбой поиска — это ошибка, а не null. Если поисковик не ответил ни на один запрос, пайплайн возвращает ошибку и ничего не пишет в справочник. Иначе компания на 30 дней получила бы ложное «сайта нет». Ситуация реальная: во время работы Exa оказался недоступен без VPN.
  10. Справочник и кэш.
    • data/directory.csv хранит и найденные сайты, и отрицательные ответы с датой проверки: «сайта нет» перепроверяется через 30 дней. Формат CSV выбран, чтобы справочник можно было открыть в Excel и перенести в другую систему одной загрузкой.
    • Ответы поиска, загруженные сайты и ответы LLM кэшируются на диске: повторные прогоны и сравнение режимов почти ничего не стоят и воспроизводимы.

Ограничения и что улучшить

  • Поиск: Exa и DuckDuckGo слабо покрывают малый бизнес РФ и доступны только через VPN → Yandex Search API.
  • Сайты на JS и защита от ботов (Wildberries, Ашан): нужен headless-браузер; сейчас выручают Exa contents и страницы из выдачи.
  • Бренды без реквизитов на сайте подтверждаются плохо → WHOIS (владелец домена), товарные знаки, домены почты из ЕГРЮЛ (платные тарифы DaData).
  • Цитаты: модель иногда подмешивает данные карточки → давать ей только фрагменты страниц или проверять числа карточки отдельно.
  • Один ИНН — много сайтов: проверяется до 8 доменов за итерацию; полный список даст обход «от домена к ИНН» (Задание 1).
