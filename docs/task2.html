Задание 2. Пайплайн «ИНН → сайт» (Web Search + LLM)

Код: {{REPO_URL}}. Python 3.12, запуск: uv run python -m site_finder 7721581040 → {"domain": "dadata.ru", "sites": ["dadata.ru"]}. domain — основной сайт (формат из задания) или null; sites — все подтверждённые домены (совместимо с data.sites[]).

Общая логика

Это workflow с агентным шагом, а не автономный агент. Шаги задаёт код. LLM принимает решения в двух местах: оценивает каждый найденный сайт и, если подтверждённого сайта нет, сама формулирует новые поисковые запросы. Принцип: доказательства собирает код, LLM интерпретирует контекст, решение принимает прозрачное правило.

ИНН → валидация (контрольная сумма) → справочник data/directory.csv (уже проверяли? → ответ)
    → карточка ЕГРЮЛ/ЕГРИП: название, ОГРН, адрес, статус, e-mail
    → поиск: Exa + DuckDuckGo по шаблонам  "ИНН" · "ОГРН" · название + город (ИП: ФИО + город)
    → кандидаты: домены из выдачи + домены, упомянутые на страницах с ИНН компании
                 (карточки агрегаторов: «Сайт: …», «E-mail: info@…») + домен почты из ЕГРЮЛ
    → проверка (код): главная + Реквизиты/Контакты/О компании/Политика ПДн + страницы домена из выдачи
                      → флаги ИНН / ОГРН / название, фрагменты ±250 символов вокруг совпадений
    → GigaChat-2-Max (function calling): вердикт по каждому кандидату + цитата-доказательство
    → правило → нет подтверждённого сайта? GigaChat предлагает до 3 новых запросов → ещё одна итерация
    → {"domain", "sites"} + запись в справочник + трассировка logs/<ИНН>.json

Ключевые технические решения

  1. Проверка реквизитов кодом до LLM. ИНН/ОГРН ищутся регулярным выражением, с учётом пробелов («7721 581 040»). Это главный рычаг точности: факт, а не мнение модели.
  2. LLM даёт категорию, а не вероятность. Вероятности, которые модель выдаёт словами, не откалиброваны. Вместо них — вердикт из фиксированного набора: own_site / group_site / third_party_mention / unrelated. Ключевая задача LLM — отличить собственный сайт от упоминания третьей стороной. На ИНН DaData поиск выдаёт десятки сайтов автодилеров, где «ООО "Дейта Кью"» указано в политике ПДн как обработчик данных: ИНН на странице есть, но сайт чужой.
  3. Вместо «reason» — цитата, которую проверяет код. Свободное обоснование в ответе не нужно. Модель обязана привести фрагмент страницы, на котором основан вердикт. Код проверяет, что все числа из цитаты есть в тексте страницы и что совпадает не меньше 85% слов. Дословное совпадение не требуется: модель переписывает таблицы реквизитов в списки, и при строгой проверке мы теряли верный sberbank.ru.
  4. Прозрачное правило решения:
    • принять, если ИНН или ОГРН есть на сайте и LLM подтвердила own_site или group_site;
    • принять, если на сайте есть название, есть независимый источник (домен упомянут на странице с ИНН компании или совпадает с почтой из ЕГРЮЛ) и LLM подтвердила own_site;
    • иначе — null.
    Правило настраивается на размеченной выборке, каждое решение видно в трассировке.
  5. Без LangGraph. Поток почти линейный: один цикл максимум из двух итераций и одна развилка. Всё, ради чего берут LangGraph, здесь не нужно: сохранение состояния, возобновление после сбоя, участие человека, параллельные ветки, несколько агентов. Обычный Python короче, логика видна целиком, меньше зависимостей.
  6. Workflow вместо автономного агента, где LLM сама выбирает инструменты: предсказуемая стоимость (не больше 2 итераций, до 8 кандидатов на итерацию), воспроизводимость, качество легко измерить. Платим за это гибкостью в нестандартных случаях.
  7. Агрегаторы распознаются по общим признакам, а не по чёрному списку. Агрегаторов реквизитов сотни: при разметке выборки встретились десятки, которых не было в стартовом списке. Признаки «страницы-каталога»: ИНН или ОГРН компании в URL, на странице четыре и больше разных ИНН. Такие домены и площадки (соцсети, маркетплейсы, бесплатная почта) получают низкий приоритет, но не исключаются: у Ozon, HeadHunter, Яндекса это и есть собственный сайт.
  8. Устойчивость к отказам GigaChat. Фильтр модели срабатывал (finish_reason=blacklist) на пакете кандидатов, где была страница о санкциях, и ответ пропадал для всех кандидатов сразу. Теперь при отказе каждый кандидат оценивается отдельным запросом, отказ затрагивает только «чувствительную» страницу.
  9. Справочник и кэш.
    • data/directory.csv хранит и найденные сайты, и отрицательные ответы с датой проверки: «сайта нет» перепроверяется через 30 дней. Формат CSV выбран, чтобы справочник можно было открыть в Excel и перенести в другую систему одной загрузкой.
    • Ответы поиска, загруженные сайты и ответы LLM кэшируются на диске: повторные прогоны и сравнение режимов почти ничего не стоят и воспроизводимы.

Ограничения и что улучшить

  • Покрытие поиска. Exa и DuckDuckGo слабо индексируют малый бизнес РФ. Следующий шаг — Yandex Search API: для российских компаний покрытие заметно выше.
  • Сайты на JavaScript и защита от ботов (Яндекс, Сбер): нужен headless-браузер. Сейчас частично выручают Exa contents и страницы домена из поисковой выдачи.
  • Сайты без реквизитов подтверждаются только по названию и независимому источнику. Для брендов, не совпадающих с юрназванием, это слабое место.
  • Скорость: 30–90 с на ИНН. Основное время уходит на загрузку сайтов и LLM. Для массового заполнения нужны параллельная обработка ИНН и бюджет запросов.
  • Выборка маленькая (55 ИНН): доверительные интервалы метрик широкие. Для решения о запуске нужен эталон из раздела 3 Задания 1.
